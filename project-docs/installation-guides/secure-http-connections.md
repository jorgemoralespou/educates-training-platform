(secure-http-connections)=
Secure HTTP Connections
=======================

When installing Educates into a Kubernetes cluster, one of the key decisions you will need to make is how secure HTTP connections (HTTPS) are handled. Depending on your network environment, the answer can range from straightforward to quite involved. This is especially common in corporate environments where SSL certificates, DNS, and proxy infrastructure may be managed by separate operations teams.

This guide describes the most common scenarios along with how each maps onto the Educates configuration. For the configuration file syntax, refer to the [configuration settings](configuration-settings) documentation.

Wildcard DNS as a prerequisite
------------------------------

Regardless of which approach you use for handling secure connections, all scenarios require that a wildcard DNS entry be configured for the ingress domain used by Educates. This is typically achieved by creating a wildcard CNAME record in your DNS provider, pointing at the IP address of whatever sits in front of your Kubernetes cluster, whether that is the cluster's own ingress router, a separate proxy server, or a CDN edge network.

For example, if your ingress domain is ``workshops.example.com``, you would need a DNS entry for ``*.workshops.example.com`` that resolves to the appropriate IP address.

When using the GKE or EKS configuration kinds, this DNS configuration is handled for you automatically through ``external-dns``. In other environments, you will need to arrange for this DNS entry to be created, which may require coordinating with your network or operations team.

How certificates are configured in v4
-------------------------------------

The `EducatesClusterConfig` resource always carries a certificates configuration; how the wildcard certificate comes to exist depends on the provider you select:

* **ACME, fully managed** (`BundledCertManager` with an ACME issuer): the operator installs cert-manager and obtains a wildcard certificate from [Let's Encrypt](https://letsencrypt.org/) using a DNS01 challenge against your cloud DNS zone. This is what the `EducatesGKEConfig` (CloudDNS) and `EducatesEKSConfig` (Route53) kinds configure, and renewal is automatic. Wildcard certificates require the DNS01 challenge, as Let's Encrypt does not issue wildcards via HTTP01, which is why these scenarios need DNS provider credentials (Workload Identity / IRSA).
* **Custom CA, fully managed** (`BundledCertManager` with a CustomCA issuer): the operator installs cert-manager and issues the wildcard certificate from a CA you supply as a Secret. Name the CA key pair cert-manager signs with in `customCA.caKeyPairSecretRef`: a Secret holding the CA certificate under `tls.crt` and its private key under `tls.key`, and optionally the root certificate under `ca.crt`. The operator checks that the Secret holds both keys and that its certificate is a CA before installing anything, and reports a problem on the `CertificatesReady` condition. When the CA is an intermediate and Educates components should trust a different certificate, such as its root, name a CA trust Secret holding that certificate under `ca.crt` in the optional `customCA.caCertificateSecretRef`. Both references take an optional `namespace`, which defaults to the operator namespace. This is what a local laptop install with a custom ingress domain uses when no wildcard certificate for the domain is cached: `educates local secrets add ca <name>` generates or registers a root CA that stays on the laptop, and the deploy mints from it a CA key pair limited to the ingress domain, pushes that key pair and the root's CA trust Secret into the `educates-secrets` namespace, and references them as `customCA.caKeyPairSecretRef` and `customCA.caCertificateSecretRef`. A local install with no ingress domain set instead defaults to the `None` provider below.
* **Static certificate** (`StaticCertificate`): you already have a wildcard certificate, bought, issued by a corporate CA, a Cloudflare origin certificate, or generated with `certbot` or `mkcert`, and Educates serves it as it is. The operator installs no cert-manager and creates no `ClusterIssuer` or `Certificate`. Name a Secret holding the certificate under `tls.crt`, optionally followed by its intermediate certificates, and its private key under `tls.key` in `staticCertificate.tlsSecretRef`. When the certificate is issued by a CA that is not publicly trusted, name a CA trust Secret holding that CA's certificate under `ca.crt` in `staticCertificate.caCertificateSecretRef`, so Educates components trust it. Both references take an optional `namespace`, which defaults to the operator namespace. The operator checks the certificate before serving it and reports each problem on the `CertificatesReady` condition with its own reason: `WildcardCertificateNotFound` or `WildcardCertificateIncomplete` when the Secret or one of its keys is missing, `WildcardCertificateUnparseable` when `tls.crt` or `tls.key` does not parse, `WildcardCertificateKeyMismatch` when the key does not belong to the certificate, `WildcardCertificateDomainMismatch` when its SANs do not include `*.<domain>`, `WildcardCertificateExpired` once it has expired, and `WildcardCertificateUntrusted` when a CA trust Secret is named and the certificate's chain does not verify against it. It copies only `tls.crt` and `tls.key` into a Secret named `educates-wildcard-tls` in its own namespace, publishes that Secret as `status.ingress.wildcardCertificateSecretRef`, and keeps the copy current when the Secret you named changes, so renewing the certificate means updating that Secret in place. A certificate that expires while Educates runs turns `CertificatesReady` to `False` without any change on your part. A local laptop install selects this provider when exactly one cached wildcard certificate that has not expired covers the ingress domain: `educates local secrets add tls <name>` caches the certificate, and the deploy pushes it, together with any cached CA certificate its chain verifies against, into the `educates-secrets` namespace and references them as `staticCertificate.tlsSecretRef` and `staticCertificate.caCertificateSecretRef`; see [the local environment guide](custom-ingress-domain). Other installs select it through the `EducatesConfig` escape hatch (see [configuration settings](configuration-settings)) or by applying the `EducatesClusterConfig` yourself.
* **Your cert-manager** (`ExternalCertManager`): reserved for a cert-manager that already runs in your cluster, with Educates requesting the wildcard certificate from your `ClusterIssuer`. It is not supported yet, and the operator rejects it with `ValidationSucceeded` set to `False`. Until it is, have your cert-manager issue the wildcard certificate and name the Secret it writes with the `StaticCertificate` provider, which follows the renewals cert-manager makes to that Secret, or use Inline mode.
* **No in-cluster TLS** (`None`): the operator installs no cert-manager and issues no certificate, and Educates serves the cluster over plain HTTP. Select this with `ingress.insecure` on the local configuration for a laptop cluster, or with the `None` certificates provider directly. Set `ingress.protocol: https` alongside the `None` provider when TLS is terminated outside the cluster (see External proxies and CDNs below), so generated URLs use the right scheme even though the cluster presents no certificate.

In Inline mode Educates installs no certificate machinery and uses the certificate you already have. Name its `kubernetes.io/tls` Secret, holding `tls.crt` and `tls.key` valid for `*.<domain>`, in `inline.ingress.wildcardCertificateSecretRef`, and, when it is signed by a CA that is not publicly trusted, a CA trust Secret holding that CA's certificate under `ca.crt` in `inline.ingress.caCertificateSecretRef`. Both references take an optional `namespace`, which defaults to the operator namespace. The `EducatesInlineConfig` kind's `wildcardCertificateSecret` and `caCertificateSecret` name Secrets in the operator namespace; use the `EducatesConfig` escape hatch to keep them elsewhere. The operator checks the wildcard certificate as it checks a `StaticCertificate`, against the CA trust Secret when you name one, and reports a problem on the `CertificatesReady` condition with the same reasons. It publishes the wildcard certificate Secret, with its namespace, as `status.ingress.wildcardCertificateSecretRef`, and updates the status when either Secret changes.

In all cases other than the `None` provider, TLS is terminated by the cluster's ingress controller, and Educates handles HTTPS natively. With the `None` provider the cluster serves plain HTTP, either for a local insecure install or behind an external proxy that terminates TLS for it.

Educates components never read the Secret holding your CA. Whenever a CA is configured, the operator derives a Secret named `educates-ingress-ca` in its own namespace that holds a single key, `ca.crt`, and never a private key. With a custom CA in Managed mode, its certificate comes from the CA trust Secret when you name one, otherwise from the `ca.crt` of the CA key pair, otherwise from the root-most certificate of the key pair's `tls.crt` chain. With a `StaticCertificate` and in Inline mode it comes from the `ca.crt` of the CA trust Secret, and any other key that Secret holds, a private key included, is ignored. The operator keeps it up to date when that source Secret changes and publishes it as `status.ingress.caCertificateSecretRef` of the `EducatesClusterConfig`. The session manager, lookup service, training portals and workshop sessions trust the ingress certificates through it, and so do the cluster nodes, through the node CA injector that the session manager installs whenever a CA is configured, unless `nodeCATrust.mode` on the `SessionManager` resource is `Disabled`. With a custom CA the CA's private key stays in the namespace of the CA key pair and in the `cert-manager` namespace, where the operator copies it for cert-manager's issuer. With a `StaticCertificate` no CA private key is involved at all.

A CA override on the `SessionManager` resource, `ingressOverrides.caCertificateSecretRef`, follows the same rule. It names a CA trust Secret holding `ca.crt`, with an optional `namespace` that defaults to the operator namespace, and the operator copies its `ca.crt` alone into a Secret named `educates-session-manager-ingress-ca` in its own namespace, which the session manager, and the training portals and workshop sessions it creates, receive in place of `educates-ingress-ca`. When that Secret is missing or holds no valid certificate under `ca.crt`, the `SessionManager` reports `Ready` as `False` with a reason naming the problem.

The provider is chosen when Educates is installed and cannot be changed afterwards: the Kubernetes API server rejects an update to `ingress.certificates.provider`, and `educates admin platform deploy` reports that the certificate provider cannot change. To switch providers, delete the installation with `educates admin platform delete` and deploy again, or install into a new cluster. Deleting the installation removes cert-manager only when the provider is `BundledCertManager`, so a cert-manager you installed yourself stays in place.

External proxies and CDNs
-------------------------

In some environments, a separate proxy server or CDN (Cloudflare, an AWS ALB with an ACM certificate, Cloudflare Tunnel) sits in front of the Kubernetes cluster, terminates the public TLS connection, and forwards traffic inward.

If the proxy **re-encrypts** traffic toward the cluster using a private certificate (for example a Cloudflare origin certificate, with the Cloudflare SSL mode set to "Full"), this is just the static-certificate scenario from the cluster's point of view: supply the private certificate (and its CA) as the static wildcard certificate.

If the proxy forwards **plain HTTP** to the cluster (Cloudflare "Flexible", Cloudflare Tunnel, the typical ALB+ACM listener), the cluster itself terminates no public TLS, but Educates must still generate `https://` URLs for the public-facing domain. Assert this with `externalTLSTermination: true` in the `EducatesGKEConfig`, `EducatesEKSConfig` or `EducatesInlineConfig` configuration kinds. Underneath, this selects the `None` certificates provider with `ingress.protocol: https`, so the operator issues no in-cluster certificate while the generated URLs stay `https`. The same combination is reachable directly via `EducatesConfig` or when applying the custom resources yourself.

Because the `None` provider issues no certificate, the GKE and EKS kinds no longer require `acme` settings, and Inline mode no longer requires a `wildcardCertificateSecret`, when `externalTLSTermination` is set.

When fronting the cluster with a proxy that traverses public networks, restrict inbound traffic to the proxy's published IP ranges so traffic cannot bypass the proxy's TLS and protections.

HTTP-to-HTTPS redirection and workshop services
------------------------------------------------

Many proxies and CDN providers offer the ability to force HTTP-to-HTTPS redirection at their edge (Cloudflare's "Always Use HTTPS", ALB redirect listener rules). This works well for the Educates training portal and other Educates services, which are designed to be accessed over HTTPS. However, individual workshops may deploy their own applications and create ingress resources for services that only handle HTTP. When the external proxy forces all traffic to HTTPS and forwards requests with headers such as ``X-Forwarded-Proto: https``, the interaction with the ingress controller's own redirect logic can lead to unexpected behaviour such as redirect loops or failed connections for these workshop services.

If your environment uses an external proxy, the recommended approach is to configure the proxy so that it does not force HTTP-to-HTTPS redirection — let applications within the cluster handle redirection themselves. If forced redirection cannot be avoided, verify that workshops which create their own ingress resources for HTTP services still work correctly in your environment; behaviour varies with the exact proxy and ingress controller combination, so test with your specific stack.

Summary
-------

```text
| Scenario                          | v4 configuration                                          |
|-----------------------------------|-----------------------------------------------------------|
| Managed ACME (Let's Encrypt)      | EducatesGKEConfig / EducatesEKSConfig (BundledCertManager) |
| Managed with your own CA          | BundledCertManager + CustomCA (local: secrets add ca)     |
| Existing cert-manager in cluster  | StaticCertificate with the Secret it issues, or Inline    |
|                                   | (ExternalCertManager is not supported yet)                |
| Wildcard certificate in hand      | StaticCertificate (local: secrets add tls) / Inline       |
|                                   | wildcardCertificateSecret                                 |
| Proxy re-encrypting to cluster    | StaticCertificate with the private certificate            |
| Proxy forwarding plain HTTP       | externalTLSTermination: true (None provider, protocol     |
|                                   | https; no in-cluster certificate issued)                  |
| Plain HTTP, no TLS at all         | ingress.insecure: true (Local) / None provider, protocol  |
|                                   | http                                                       |
```

In all cases, the ingress domain must be set to the wildcard domain for which DNS has been configured.
